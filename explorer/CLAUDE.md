## Project Overview

Kinetica Graph Explorer (version tracked in the `EXPLORER_VERSION` constant, ~line 46) — a React-based single-page application for exploring graph data structures stored in a Kinetica GPU database.

**`KineticaGraphExplorer.html`** — Standalone HTML file, all dependencies via CDN, Babel transpiles JSX in-browser. Open directly in a browser, no build step needed.

There is no package.json, no build system, no test framework, and no linting configuration.

User-facing features and screenshots live in `README.md` — this file documents code structure for future Claude sessions.

## Development

Edit `KineticaGraphExplorer.html` and open/refresh in a browser. No build or install steps.

When making release-tagged changes, run `./update-version.sh` (sibling script) to sync `EXPLORER_VERSION` (~line 46) with the latest git tag — parses `release/v7.2.3-ga-13` → `7.2.3.13`. Idempotent (no-op if already in sync); exits non-zero and leaves the file untouched if no usable tag exists. Manual bumping still works for ad-hoc releases.

## Architecture

### Component Hierarchy

`App` (root) manages all top-level state: graphs, credentials, labels, ontology, picking mode, and split-pane layout. Child components:

- `Sidebar` — Server connection (URL, credentials, profile switching via `DEFAULT_PROFILES`), session Load/Save buttons, Auto-run toggle, version number, optional `📖 Docs` link. **List area**: tabbed toggle `[Graphs N] [Tables M]` controls whether the sidebar list shows graphs or tables; default `Graphs`. **`Connect & List`** button fetches both lists in one call (`/show/graph` for graphs, SQL against `INFORMATION_SCHEMA.TABLES` for tables — `/show/table` with empty name returns schemas, not tables, so SQL is used; system schemas like `SYSTEM`, `sys_sql_temp`, `pg_catalog`, `information_schema` are filtered out). **Filter input** narrows the visible list by case-insensitive substring (toggling lists clears the filter). **Collapse handle on the divider** — a small SVG-chevron tab (`24×56`, rounded right edge) sits half-attached to the sidebar's right border at vertical-middle so it visually reads as the rail's pull-handle, IDE-style. Direction flips with state (`‹` expanded → `›` collapsed). Implemented with `position: fixed` (not `absolute`) because the sidebar's `overflowY: auto` would otherwise clip an overflowing absolute child; the left coordinate auto-snaps `308 → 16` between expanded (320 px) and collapsed (28 px) widths. Collapsed rail shrinks to 28 px and shows just a vertical "Graph Explorer" label beside the handle. State `sidebarCollapsed` in App, default false. **Graph rows show a compact edge-count badge** (green) — edge count compacted via `compactNum` (`491k`, `13.1M`, etc.) with a full nodes+edges tooltip on hover. Counts come from `/show/graph`'s aligned `num_nodes`/`num_edges` arrays captured into `graphSizes: { name → {nodes, edges} }` at connect/refresh time. A small **sort toggle** (`A↓Z` ↔ `#↓`) sits next to the filter input — flips between alphabetical name and edges-desc order (stable tiebreak by name). **`+ Create` / `+ Query` / `+ Solve` / `+ Match` actions** live in the `DashboardHeader` (next to the graph stats), not in the sidebar. The Create button (green) opens a Create-Helper-mode QueryPanel with an empty `CREATE OR REPLACE DIRECTED GRAPH ...` template — same panel that used to be reachable from the now-removed `+ New` sidebar button. **Right-click any list item** opens a context menu — for **Graphs**: `Open`, `Show Create Statement`, `Modify` (opens a Create-Helper panel pre-filled from the parsed CREATE statement), `Delete…` (red, confirmation modal then `/drop/graph`), `Copy name`; for **Tables**: `Open (Preview rows)`, `Schema (DESCRIBE)`, `Copy name`. Profile switching clears both lists + `listMode` (defaults back to `Graphs`)
- `DashboardHeader` — Split-aligned layout matching `hSplit` pane proportion. Left side (`hSplit%`): graph name, N:/E: counts (blue/green), color-coded progress bar (blue=nodes, green=edges), separator, the four action buttons **`+ Create` (green `#00b894`) · `+ Query` (purple `#6c5ce7`) · `+ Solve` (pink `#fd79a8`) · `+ Match` (orange `#e17055`)**, then the kind-aware minimized panel pills (`C1/C2…` create green, `Q1/Q2…` query purple, `T1/T2…` table purple, `S1/S2…` solve pink, `M1/M2…` match orange — first-letter switch on `mp.label.charAt(0)` drives both border + bg color). Per-kind sequential numbering across the full `queryPanels` array (not just minimized ones) so labels survive minimize/restore. Right side (`1-hSplit%`): `Pick` + Auto-refresh + timestamp. Separator aligns with label chart boundary
- `SummaryCards` — Labeled/unlabeled node/edge counts with distinct label counts
- `LabelChart` — Doughnut chart (Chart.js) + interactive table for label distribution. Table supports clickable column headers to sort by label name (alphabetical) or count (default). Row colors always match the chart via `colorIdxMap` lookup
- `OntologyViewer` — Graphviz WASM rendering of graph ontology DOT with D3 zoom/pan and node/edge picking. Always visible once graph loaded; clears to "No ontology available" when `dotString` is null (e.g., graph with no labels). Header bar includes Full/NKey/EKey schema toggles (auto-reload ontology on change), `↻ Refresh` button, Reset View button, and `⤢` maximize / `▣ Restore` button (full viewport overlay, Esc to restore)
- `CanvasGraph` — force-graph (force-graph library) 2D visualization for non-WKT graphs. Always visible once graph loaded (black canvas placeholder when no data). Single-line responsive header: title + compact stats + selected label filters (left), flex node/edge sliders + viz limit + `↻ Pull+Visualize` button (right, never clipped). Colors match LabelChart via combo key color map. Click-to-copy node ID + node detail lookup from source table. `⤢` maximize / `▣ Restore` button. Supports both NAME and ID column schemas
- `DeckMapView` — **Default geo renderer** (deck.gl + MapLibre GL). Handles any graph size including 27M+ edges at 60fps via WebGL GPU rendering. **Map-pick clipboard handoff to Solve/Match constants**: every map click (whether on an edge or empty area) copies the bare `<lon> <lat>` coord pair (space-separated, no quotes, no `ST_GEOMFROMTEXT` wrapper) to the clipboard. The Solve/Match Constants-mode focus-fill drops in the full `ST_GEOMFROMTEXT('POINT(x y)')` template with the `x y` portion pre-selected — Ctrl+V then replaces just those coords, so a full-WKT clipboard would double-wrap. The lon/lat overlay shows `✓ copied` for 1.5s. The previous "copy edge id on edge pick" behavior is removed — the edge detail strip still appears on edge pick, but the clipboard always carries the bare coord pair. Binary attribute arrays (Float32Array coords, Uint8Array colors) uploaded directly to GPU — zero JS object overhead. Brighter geo-optimized color palette. WebGL antialiasing enabled. Edge picking via click (DOM-managed detail strip — no React re-render, no flicker). Tries numeric then string match for edge ID lookup. Click shows lon/lat coordinates in header. `widthMinPixels: 2` for easier pick target. Label filtering rebuilds binary arrays. Renderer toggle: `Auto/Deck.gl | Canvas | Deck.gl | WMS`. `⤢` maximize / `▣ Restore` button. **Street-map basemap overlay** — `🌐 Off | Light | Color` segmented control in the header. Both CartoDB raster sources (`light_all` for Light, `rastertiles/voyager` for Color) are added at map init; switching adjusts `raster-opacity` (0.75 active / 0 hidden) on each layer in place — no map re-init, no tile re-fetch on toggle. A flat `#0a0a1a` background layer sits beneath both for the `off` state. State (`basemapStyle`, default `'light'`) is owned by `App` and passed down as `basemapStyle` + `onChangeBasemapStyle`
- `MapView` — Legacy canvas-based geo renderer (available via Canvas toggle). Pre-parsed WKT→Float32Array coords per batch, color-batched drawing, rAF-throttled, adaptive LOD, progressive rendering. Edge picking pinned-highlights the edge (dark halo + bright green stroke) and looks up the full source-table row via id-based query with **idCol auto-probe** (mirrors DeckMapView): if `edgeSourceTable.idCol` wasn't extracted from the create statement, probes one record from the source table and resolves the id from `EDGE_ID` / `id` / `ID` / `edge_id` / first-column. Tries numeric `idCol = N` then quoted `idCol = 'N'`. Falls back to the synthetic `{EDGE_ID, NODE1_WKTPOINT, NODE2_WKTPOINT}` if no id column is resolvable. Label filtering supported
  - **WMS auth via fetch + blob URL**: `<img src="/wms?…">` can't carry `Authorization: Basic`, so deployments behind auth return 401. The tile loader fetches the URL with `fetch()` (header attached), wraps the body in `URL.createObjectURL(blob)`, and sets THAT on the `<img>`. Previous blob URLs are revoked when the next tile lands to avoid leaks across rapid pan/zoom.
  - **WMS server-side** (user-selected only): Kinetica `/wms` endpoint renders PNG tiles via `setupWmsMode()` — no `get/graph/entities` needed. Four WMS sub-styles (`Auto | Heat | Raster | CB`): **Auto** uses heatmap at low zoom (<5x relative), raster/CB at deep zoom; **Heat** forces heatmap (`jet` colormap; `BLUR_RADIUS` scales with zoom: `max(2, min(24, round(relativeZoom * 3)))` — keeps the colormap spectrum spread comparable as you zoom in, otherwise per-pixel density drops and the jet ramp collapses to its cool end). **WMS edge picking**: click (no drag) on the rendered tile fires a server-side `STXY_DWITHIN(<geoCol>, lon, lat, tolDeg, 0)` query via `/execute/sql`. Pixel→lon/lat uses the current bbox; tolerance is `5 * bboxWidth / containerWidth` so the click target stays ~5 px regardless of zoom. Result lands in the standard `nodeDetail` strip — same as Canvas/Deck.gl edge picking. Click vs drag is disambiguated by `<5 px` movement in `handleMouseUp`; **Raster** forces plain raster; **CB** forces class-break (requires non-JSON label column, top 20 labels). `cb_raster` uses `REPLACE()` SQL for JSON label columns. BBOX auto-computed via `ST_MINX/MAXX/MINY/MAXY` SQL, aspect-ratio adjusted. Offscreen image loading. Zoom (cursor-centered wheel) + pan (drag-on-release). Label filtering via `LABEL_FILTER`. `⤢` maximize / `▣ Restore` button
- `QueryPanel` — Self-contained floating SQL window (multiple instances supported) with minimize/maximize/restore/close buttons. **Run-output persists across minimize→restore (and across session save/load when small enough)**: `stateRef.current.result` carries the raw `/execute/sql` response, the App-level `onMinimize` snapshots it onto `panel.initialResult`, and `QueryPanel`'s `useState(result)` seeds from `initialResult` on remount. Restore from the C*/S*/M*/Q*/T* pill brings back View Results / Visualization / Map / Video tabs verbatim without re-firing the SQL. **Session persistence**: `buildSession` also stringifies each panel's `result` and includes it as `cachedResult` if the JSON is **≤ 2 MB** (the `SESSION_RESULT_CAP`). Over-cap panels are saved without `cachedResult` — on load they restore empty and the existing rule applies (Query/Table auto-rerun if `autoRunQueries` is on, Create/Solve/Match wait for the user to click Run, preserving today's behavior for big match outputs). `loadSession` threads `cachedResult` through as `initialResult` and forces `autoRun: false` when present so we don't redo the work. Minimize collapses to a kind-aware pill in the header bar (`Q*` query, `T*` table, `C*` create, `S*` solve, `M*` match — state preserved via stateRef snapshot). Five modes, set via props at creation time:
   - **Query** (default): collapsible **Query Helper** at top — generates GQL from multi-label/entity selections using ontology BFS with waypoints and direction-aware arrows. SQL editor + View Results + Visualization tabs.
   - **Table-query** (`hideQueryHelper={true}`): Query Helper hidden. Used when panel is opened from a Table click/context-menu — Helper is GQL-only and irrelevant for plain table SQL. Auto-runs `SELECT * FROM <table> LIMIT 100` (or `DESCRIBE <table>` from the Schema action).
   - **Solve-graph** (`solveHelper={true}`, opened via the `+ Solve` button in `DashboardHeader`): a pink-accent Create-Helper-style panel for the `/solve/graph` endpoint. Iterates over `endpointGrammar.solve.components` (typically `WEIGHTS`, `RESTRICTIONS`, `SOLVETARGETS` ×2 for source + destination — the App-side de-dup keeps both with a `_N` suffix on the key but emits the bare `SOLVETARGETS` name in SQL). Top section: `Solver type` dropdown (sourced from the union of all configuration + option `filtervalues`, fallback `DEFAULT_SOLVERS`) and an optional `Solution table`. Each component section reuses the Create Helper's section UI: default-table + bare-column rows, combo grouping, collapsible header. Configurations are filtered against the current solver type — only those with no `filtervalues` or whose `filtervalues` include the selected solver are offered in the dropdown. OPTIONS section follows the same filter rule (suggestions come from `endpointGrammar.solve.options`).
     - **Auto-populated defaults**: on panel mount and on every solver-type change, `applicableGrammarOptions(solveGr, shSolverType)` pulls every grammar option whose `filtervalues` explicitly contains the current solver (skipping `internal === 'true'`) and pre-fills the OPTIONS list with its `default` value.
     - **Boolean options get a `true`/`false` dropdown**: the value cell looks up the row's key in `gr.options[i].type` — if it's `boolean`, the input is replaced by a 2-choice `<select>` so the user can pick instead of typing.
     - **`Output` dropdown next to Solution table**: when the current solver/method has ≥ 2 applicable output schemas (per `outputSchemasForMethod(gr, method)` which walks `endpointGrammar.{solve|match}.outputs` and filters columns by `filtervalues`), a small `Output: [default | 1: cols… | 2: cols…]` dropdown sits between the Solution-table input and the `auto-drop` checkbox. **Indexing is 1-based among the filtered (applicable) schemas, not the global outputs array** — so `match_isochrone`'s POLYGON schema is `2` even if it's the 16th entry overall. `outputSchemasForMethod` uses a running counter that increments only when a schema has applicable columns. Options are labeled with a column summary (`1: SOURCE, x, y, z` / `2: SOURCE, POLYGON (wkt)` — `(wkt)` flagged when `format === 'wkt'`). The picked index drives a dedicated state (`shResultTableIdx` / `mhResultTableIdx`), and SQL generation injects `result_table_index = 'N'` into the OPTIONS KV_PAIRS at emit time (overriding any same-key entry in the OPTIONS list). Empty = server default. *Important grammar parsing detail*: the JSON response uses `column` + `subtype` (not `name` + `format`) — `normalizeEndpoint` accepts either spelling so the outputs schema actually populates. Each auto-added row is tagged `from: 'grammar'`; user-added rows (`+ Add option`) and any row the user edits are tagged `from: 'user'` so they survive subsequent solver switches. `mergeGrammarOptions` keeps user-tagged rows verbatim and replaces only the grammar-tagged ones on switch. Same effect applies to the Match Helper against `matchGr` + `mhSolveMethod`. For SOLVETARGETS-typed sections (SOURCE_NODES / DESTINATION_NODES), the row alias is collapsed via `shAliasFor` → `chGenericId(id, 'NODES')`, so `NODE_NAME` / `NODE_ID` / `NODE_WKTPOINT` all render and emit as just `AS NODE`. Configurations whose required identifiers contain `NODE_X` or `NODE_Y` are filtered out — XY-pair geometries break the generic collapse and are rarely used.
     - **Constants mode**: SOLVETARGETS sections show a `Table | Constants` toggle in the section header (sparse state `shSectionMode[compKey] = 'constants'`). In constants mode the Default-table input is hidden and each row's value is treated as a literal SQL expression.
     - **N-tuple sub-select grouping**: rows added together by a single configuration pick share a `groupId`, and `shBuildSection` / `mhBuildSection` collapse same-groupId rows into one combined sub-select — e.g., picking the `SAMPLE_ID + SAMPLE_WKTPOINT` config under `match_isochrone` and filling both rows emits `(SELECT 1 AS ID, ST_GEOMFROMTEXT('POINT(-122 37)') AS WKTPOINT)` rather than two separate sub-selects. Single-literal "`+ Add single literal`" rows (ungrouped) still emit one sub-select per row. The constants-mode UI keeps the configuration dropdown visible (primary entry for n-tuples) and offers the button as a quick fallback. Row placeholders are type-aware via `constantHintFor(r.id)` — keyed on the **original identifier** (e.g. `NODE_WKTPOINT`), not the displayed alias, so Solve's `NODE` collapse doesn't lose the WKT/ID/NAME context.
     - **Focus-fill template**: when the user focuses an empty constants-mode input AND `constantHintFor(r.id)` returns a meaningful template (not the generic "literal value"), the template is dropped into the field immediately and the editable bit (numeric coords inside `POINT(...)`, the body inside the outer parens, or the body between single quotes — picked by `templateEditableRange`) is pre-selected so a single keystroke replaces it. Saves typing `ST_GEOMFROMTEXT('POINT(...)` etc. `WKT|POINT|LINE|GEOM` IDs get `ST_GEOMFROMTEXT('POINT(-122 37)')`, `_ID` / `ID` get integers, `NAME` gets `'Bill'`, `TIME` gets timestamp examples, etc. WEIGHTS/RESTRICTIONS stay table-only (their multi-identifier configurations don't map cleanly to one-literal-per-row).
     - **Solution-table default + two SQL forms**: the `Solution table` field is auto-prefilled with `<schema>.solution_<graph_name>_<solver_lc>` (e.g. `ki_home.solution_san_francisco_shortest_path`) via `defaultSolutionTable(activeGraph, shSolverType)`. The auto-fill effect refreshes the value on solver-type change **only** when it still matches the auto pattern (`isAutoSolutionTable`) — user-customized names are preserved. When the field has a value, Generate emits the persistent form `EXECUTE FUNCTION SOLVE_GRAPH(GRAPH => '<active>', SOLVER_TYPE => '<x>', <COMP> => INPUT_TABLES(...), …, SOLUTION_TABLE => '<t>', OPTIONS => KV_PAIRS(...))` plus the `DROP TABLE IF EXISTS` prefix when `auto-drop` is on. When the user clears the field, Generate emits the inline form `SELECT * FROM SOLVE_GRAPH(GRAPH => '<active>', SOLVER_TYPE => '<x>', …)` (and the equivalent `SELECT * FROM MATCH_GRAPH(...)` for the Match Helper) — rows are returned directly without materializing a persistent table.
     - **Auto-drop**: when `SOLUTION_TABLE` is set and the `auto-drop` checkbox is on (default), the generated SQL is prefixed with `DROP TABLE IF EXISTS <solution_table>;` so consecutive Runs don't fail because the prior table already exists.
     - **Multi-statement execution**: `executeQuery` strips `--` line comments and `/* */` blocks, splits on `;`, and runs each statement sequentially (first error aborts).
     - **Auto-fetch solution rows**: after a successful `EXECUTE FUNCTION SOLVE_GRAPH(...)` (or `MATCH_GRAPH`) with `SOLUTION_TABLE`, the panel auto-runs `SELECT * FROM <solution_table> LIMIT 10000` and uses that as the displayed result so the user sees the solver output in the View Results tab — analogous to the post-GQL hop-results flow (sets `activeTab='results'`).
     - **`result_table_index` suffix**: when the OPTIONS contain `result_table_index`, certain solvers create a secondary table with an implicit suffix (e.g., `match_isochrone` + `2` → `<solution_table>_polygons`). The grammar doesn't expose the suffix mapping (server-side concept), so the client uses a hardcoded `SUFFIX_MAP` keyed by `<method>|<index>` for known cases plus an `INFORMATION_SCHEMA.TABLES LIKE '<solution_table>_%'` probe fallback when the mapped suffix misses — a non-fatal warning tells the user we auto-picked a sibling. If the auto-fetch fails entirely (e.g., permissions), the original run response is shown.
     - **Path viz (force-graph)**: when the fetched rows include a `nameroute` column (string of comma-separated node names per path; emitted by SHORTEST_PATH / INVERSE_SHORTEST_PATH / ALLPATHS / MULTIPLE_ROUTING / BACKHAUL_ROUTING per the grammar's `outputs` filtervalues), `solveGraphData` parses each row's sequence into chained nodes + per-path-colored links and feeds the same force-graph viz the GQL hop-results use. `effectiveGraphData = hasHops ? graphData : solveGraphData` unifies both sources behind the existing render path; the Visualization tab button label adapts (`… nodes, N paths`).
     - **Video tab**: when the response's `info.svg` carries an inline animated SVG string (server-side emit for solvers/matchers like supply-demand routes or GPS map-matching trails), a `Video` tab appears next to `Map`. Its content area dumps the SVG directly via `dangerouslySetInnerHTML` over a dark backdrop — the SVG's own animations (SMIL, CSS keyframes) play in place. The tab is not auto-selected; user clicks it. Cleared when a subsequent result lacks `info.svg`.
     - **Draggable-panel clamp**: `handleDragStart` constrains the position so the title bar can't be dragged past the viewport edges — top stays ≥ 0, bottom keeps ≥ 32 px on screen, horizontal keeps ≥ 60 px of the bar visible. A mount-time `useEffect` also snaps restored positions back into viewport. Without this the user could drag the title bar off-screen and lose the only handle for re-positioning the panel.
     - **Info-preservation across auto-fetch**: the `EXECUTE FUNCTION` response carries `info.svg`, but the subsequent `SELECT * FROM <solution_table>` auto-fetch replaces `data` with a plain row response that has no info. `executeQuery` stashes the function-call's `info` map into `preservedInfo` before the SELECT runs and splices it back onto the SELECT's `data_str` so the Video tab (and any other `info`-driven UI) still sees it. Auto-switches to the viz tab on successful solve with paths.
     - **Map viz (Deck.gl)**: shown when the solution_table includes a WKT column. Detection is a three-step chain in priority order: **(1)** column datatype (most reliable — `tableData.datatypes[i]` matching `/wkt|geometry|geom/i` — covers `SOLVERS_NODE_WKT geometry` and similar schema-typed columns regardless of name), **(2)** header substring match (`wkt` / `geom` / `polygon` / `linestring` — for older servers that don't report datatypes), **(3)** value sniff (first row whose value starts with `LINESTRING(` / `POINT(` / `MULTILINESTRING(` / `POLYGON(` / `MULTIPOLYGON(`). Detection returns an **ordered list of all matching columns** (`wktRouteCols`) by running **all three detectors and unioning the results** (deduped) — the previous short-circuit ("step 1 found something so skip 2 and 3") missed sibling geometry columns when the server tagged some as `geometry` and others as `string` (or didn't tag them at all). The first detected column is the default, but when more than one applies — e.g., SHORTEST_PATH and `match_batch_solves` output rows expose `SOURCE` + `TARGET` + `PATH` all as `geometry` — the Map tab surfaces a small picker. The picker also has an **`All`** option that overlays every detected column on the same map (one parse pass per row × column). **or** a plain x,y column pair (case-insensitive `x` / `lon` / `lng` / `longitude` plus `y` / `lat` / `latitude` — handles the single-isochrone `SOURCE/x/y/z` output). `SolveMapView` (defined just before `QueryPanel`) parses each row into a `PathLayer` feature (`LINESTRING`, plus each branch of a `MULTILINESTRING`), a `PolygonLayer` feature (`POLYGON` with optional holes, plus each polygon in a `MULTIPOLYGON` split on top-level `))(((`), a `ScatterplotLayer` feature (`POINT`, `MULTIPOINT`), or a `ScatterplotLayer` feature (x,y row). All three layers render simultaneously on the same Deck.gl + CartoDB-basemap canvas (`light_all`), pickable with autoHighlight, auto-fitting to the union bbox. One color per row via PALETTE. Single-point bbox falls back to a city-level zoom (≈12). Click a path (anywhere along its pixel width — PathLayer's built-in tolerance functions as a client-side ST_DWITHIN) to surface the full source row in a detail strip below the map (pink top border). Long WKT values are truncated at 200 chars to keep the strip readable. Auto-switches to `map` when paths aren't available but WKT is; if both nameroute and wktroute apply, the force-graph (`graph`) tab wins and the user can click `Map` for the geo view.
     - **Persistence & auto-collapse**: The Solve Helper auto-collapses (`setShShow(false)`) the moment a viz tab is shown so the viz claims the full top region — the user re-opens the helper via its `▶ Solve Helper` header to tweak. State persisted as `helper.solve` (mirror of Create Helper shape — `{ show, solverType, solutionTable, rows, sectionTable, options, expanded }`). On graph switch and post-Open-banner flows, Solve panels are preserved/minimized the same way Create panels are (they're graph-independent in terms of state).
   - **Match-graph** (`matchHelper={true}`, opened via the `+ Match` button — orange `#e17055`): mirror of Solve Helper against `endpointGrammar.match`. Single component `SAMPLES` role-renamed to `SAMPLE_POINTS` (per `ENDPOINT_ROLE_NAMES['/match/graph']`). Filterparam is `solve_method` (`markov_chain` / `match_supply_demand` / `match_od_pairs` / `match_loops` / `match_charging_stations` / `match_route_detour` / …; fallback `DEFAULT_MATCH_METHODS`). State persisted under `helper.match` with the same shape as `helper.solve` (rename `solverType` → `solveMethod`). `chGenericId` extended to strip the `SAMPLE_` prefix when component is `SAMPLES` (so `SAMPLE_WKTPOINT` → `WKTPOINT`, `SAMPLE_ORIGIN_WKTPOINT` → `ORIGIN_WKTPOINT`, etc.). `SAMPLE_X`/`SAMPLE_Y` configurations are filtered out (same break-the-generic-collapse reasoning as SOLVE). Constants mode supported on the SAMPLES section. **Add-on filtering by domain**: the grammar's `addons` array is flat with no per-add-on `filtervalues`, so `mhAddonApplies` applies a name-based heuristic on configuration-pick — `SAMPLE_SUPPLY_*` only spawns for `match_supply_demand`/`match_charging_stations`; `SAMPLE_DEMAND_*` for `match_supply_demand`; `SAMPLE_PICKUP_*`/`SAMPLE_DROPOFF_*`/`SAMPLE_RIDE_*` for `match_pickup_dropoff`; `SAMPLE_PATTERN_*` for `match_pattern`; `SAMPLE_OD_*` for `match_od_pairs`; `SAMPLE_TRIPID`/`SAMPLE_TIME` for `markov_chain` (and OD pairs for TIME). Add-ons without a domain prefix (e.g. `SAMPLE_PRIORITY`, `SAMPLE_ID`, `SAMPLE_NAME`) apply broadly. Without this, picking a single-WKTPOINT config for `match_isochrone` was spawning 20+ unrelated rows. Generate emits `EXECUTE FUNCTION MATCH_GRAPH(GRAPH => '<active>', SOLVE_METHOD => '<x>', SAMPLE_POINTS => INPUT_TABLES(...), …, SOLUTION_TABLE => '<t>', OPTIONS => KV_PAIRS(...))`. ### Kinetica API Endpoints Used

- `POST /show/graph` — List graphs (empty name), get graph label details + ontology DOT (specific name with `export_graph_schema: 'true'`). Supports internal options: `schema_node_labelkeys`, `schema_edge_labelkeys`, `schema_full_search`. Ontology auto-loads on graph selection — no separate Ontology button needed
- `POST /get/graph/entities` — Fetch graph nodes/edges directly from the graph server (preferred). Options: `entity_type` (`"node"`/`"edge"`), `offset`, `limit` (-1 for all), `concise_edge_connectivity` (`"true"` for unified int-indexed edges), `include_weights` (`"true"` to return per-edge weights). Response payload arrays — three of them, one carries data per call: `entities_int` (long), `entities_string` (string; name-id graphs only — never WKT), `entities_double` (double; WKT/geo-XY graphs **always**). Optional `entities_weight` (float, edge-aligned, stride 1) when `include_weights` is set. Plus `labels` (1-based index, may be JSON arrays for multi-label) and `info` map: `identifier_type`, `payload_type` (which array carries data — `'int'`/`'string'`/`'double'`; **dispatch on this, not identifier_type**), `total_count`, `status_message`, `concise_edge_connectivity`, `include_weights`. Default strides — nodes: int=2 `[id,label_idx]`, string=2 `[name,label_idx]`, double=3 `[x,y,label_idx]`; edges: int=4 `[edge_id,n1,n2,label_idx]`, string=4 `[edge_id,n1_name,n2_name,label_idx]`, double=6 `[edge_id,x0,y0,x1,y1,label_idx]`. Concise mode: edges always in `entities_int` as `[edge_id, v0_idx, v1_idx, label_idx]` (v0/v1 are 0-based node slot indices); WKT-graph nodes still in `entities_double` with deleted slots zero-filled `[0.0, 0.0, 0.0]`; non-WKT nodes use sentinel id=0/`""` for tombstones so indices stay stable. **WKT graphs NEVER emit `'POINT(x y)'` strings** — coordinates are always packed in `entities_double`. Client (`fetchGraphEntities`) dispatches on `info.payload_type`: `'double'` → reads coords directly from `entities_double` (stride 3 nodes / 6 edges, no regex, ~4× smaller wire size); `'int'` → `entities_int` (int graphs and concise edges); `'string'` → `entities_string` (string graphs only). Legacy `POINT(x y)` regex parsing retained as a fallback for old servers that don't emit `payload_type`. Batched fetcher uses concise mode for all graph types — one extraction path. Small graphs (<300K entities) use single-request path which synthesizes a `wktParsed` shape for WKT so the renderer code is shared
- `POST /get/records` — Fallback: fetch backing table rows for visualization; also used for node detail lookup from source table
- `POST /execute/sql` — Run SQL/GQL queries via `QueryPanel`; also used for WMS BBOX computation (`ST_MINX/MAXX/MINY/MAXY`)
- `GET /wms` — Server-side map tile rendering for large WKT graphs (>2M edges). Supports `heatmap` (fast, low zoom) and `raster` (detailed, high zoom) styles. Parameters: `LAYERS`, `GEO_ATTR`, `BBOX`, `WIDTH`, `HEIGHT`, `SRS=EPSG:4326`, `STYLES`

### Helpers

- `extractGraphTable(originalRequest, graphName)` — Parses the graph creation statement to find the backing table name
- `extractNodeSourceTable(originalRequest, graphName)` — Parses `NODES => INPUT_TABLE(S)(...)` section using balanced parenthesis matching (handles nested sub-selects). Finds original node source table and ID column. Falls back to probing table for common ID columns (`node`, `id`, `NODE_NAME`, etc.) or using first column
- `extractEdgeSourceTable(originalRequest, graphName)` — Parses `EDGES => INPUT_TABLE(S)(...)` section using balanced parenthesis matching. Returns `{ table, idCol, wktCol, labelCol }`. `wktCol` extracted from any of the valid CREATE GRAPH EDGES WKT aliases — full-line (`EDGE_WKTLINE` / `WKTLINE`), single point (`EDGE_WKTPOINT` / `WKTPOINT`), or start/end endpoint pair (`EDGE_NODE1_WKTPOINT` / `NODE1_WKTPOINT`, `EDGE_NODE2_WKTPOINT` / `NODE2_WKTPOINT`). The regex returns the first source-position match. If `wktCol` is not pinned by the create statement (e.g., `SELECT * FROM <foo>` with no explicit alias), `loadGraphDetails` runs a two-stage probe — **(1)** `/show/table` and inspects each column's `properties` array for the `wkt` tag via `detectWktColumnFromShowTable`; **(2)** if still empty, `/get/records limit:1` and scans every column's first value for a `LINESTRING/POINT/POLYGON/MULTI*` prefix via `detectWktColumn`. `setupWmsMode` repeats the same two-stage probe before issuing `/wms` and surfaces a warn toast when no WKT column is detected (instead of silently sending `GEO_ATTR=WKTLINE` that 404s). `labelCol` handles `func(col) AS LABEL` casts. Used for edge picking, WMS `GEO_ATTR`, and geo graph detection
- `resolveCol(headers, candidates)` — Fuzzy column name resolution for table preview
- `safeParse(str, fallback)` — Safe JSON.parse wrapper
- `normNodeKey(raw)` — Normalizes DOT node names like `"FEMALE:\ndance (20%)"` to keys `"FEMALE|dance"`

### Query Helper

Collapsible panel inside each QueryPanel that generates GQL queries from form inputs. Opens expanded by default; auto-collapses after generating a query (clears previous visualization). All state is preserved on collapse/expand and saved in sessions.

- **Inputs**: Source Label(s) (multi-select tag picker), Source Entity (optional), Target Label(s) (multi-select), Target Entity (optional)
- **Waypoints**: "+ Add Hop" adds intermediate constraints. Each hop row shows: hop index (large) | Node Label(s) (multi-select tags) | → | Edge Label(s) (multi-select tags) | ✕ remove. Both node and edge labels support multi-select with OR logic. Pathfinding auto-determines hop count — no manual Hops input needed
- **Multi-label (OR logic)**: Selecting multiple labels (e.g., `street_address` + `email`) means "match nodes with ANY of these labels". GQL syntax: `(a:street_address|email)`. Same for edges: `manages` + `part_of` → `-[e:manages|part_of]->`. Pathfinding tries routes from all matching ontology nodes. User-selected edge labels are preserved in generated GQL even when BFS finds a path via a single edge
- **Ontology pathfinding**: Parses `dotString` into adjacency map via regex (matches both `->` directed and `--` undirected edges; normalizes multi-label DOT names). For undirected graphs (`graph G { ... -- ... }`), adds edges in both directions and generates `-[]-` edges in GQL (no arrows). Builds reverse adjacency for bidirectional BFS. Chains through waypoints finding sub-paths. For directed graphs, respects edge direction (`dir: 'fwd'` → `->`, `dir: 'rev'` → `<-`). Edge label constraints use OR matching. `labelsToKeys` sorts results to prefer exact matches over partial (e.g., `actor` before `actor|director`)
- **GQL generation**: Uses only user-selected labels (not full ontology keys) in MATCH patterns. Uses `as` aliases in RETURN (e.g., `a.NODE as a_node`). Labels with spaces are double-quoted (e.g., `(c:"news company")`). Graph names are always double-quoted per part (e.g., `GRAPH "schema"."355_g"`). Falls back to generic untyped pattern when ontology not loaded or no path found
- **Collapsed status**: When helper is collapsed after generation, the path found info (with arrows) shows in green next to the header
- **Auto-visualization**: Query results with hop data automatically switch to the Visualization tab. No-result queries and new query generation clear the previous visualization
- **Node Detail Lookup**: Clicking a node in the visualization fetches its full record from the original node source table. Displayed as a horizontal table strip below the graph. Cleared on Generate Query or Run
- **Props needed**: `dotString`, `activeGraph`, `graphDirected`, `labelData`, `nodeSourceTable` passed from App to QueryPanel

### Node Source Table Extraction

`extractNodeSourceTable(originalRequest, graphName)` parses the graph creation statement's `NODES => INPUT_TABLES(...)` section:
- Finds all `FROM <table>` references and uses the last real table (handles multi sub-select cases like wiki_graph with constants + real table)
- Extracts the original ID column aliased as `NODE` or `NODE_ID`
- If no alias found, probes the table at fetch time for common ID columns (`node`, `id`, `NODE_NAME`, `NODE_ID`, `name`)
- App stores result as `nodeSourceTable: { table, idCol }` state, passed to QueryPanel and CanvasGraph
- Node click uses `/get/records` with `expression` filter on the source table's original ID column (tries string then numeric match)

### Kinetica `/execute/sql` Response Format

Responses are **double-wrapped**: the top-level JSON has `{ status, message, data_type, data, data_str }`. The actual payload is inside `data_str` (a JSON string that must be parsed). Once unwrapped, graph queries produce **two distinct data sources**:

**`data_str.json_encoded_response`** — Contains the **RETURN statement** columns (e.g., `bank`, `wire`, `ablabel`, `transaction`, `banking_transaction_amount`). This is what the "View Results" button displays. Column-oriented object with `column_headers`, `column_datatypes`, and `column_1`..`column_N` arrays.

**`data_str.info.gql_result`** — Contains the **hop-based path structure** (`NODE1_HOP_1`, `NODE2_HOP_1`, `EDGE_LABELS_HOP_1`, etc.). This is what the "Visualization" button uses to build the force-graph. Same column-oriented format as above.

Both use the same structure: iterate `column_1[i]`..`column_N[i]` for each row index `i`, using `column_headers` for display names.

Other fields: `data_str.info.count` (record count), `data_str.response_schema_str` (Avro schema).

### Session Save/Load

Sessions are saved as JSON files (schema version 1). The session object captures:
- `connection` — Server URL and username (password excluded)
- `graph.name` — Active graph, `selectedNodeLabels`, `selectedEdgeLabels`, `ontologyDot`
- `graph.dataFetched` — Whether table data was loaded; `graph.showForceGraph` — Whether visualization was active
- `queries[]` — Array of open query panels with `sql` text, `activeTab` state, and `helper` object (srcLabels, srcEntity, tgtLabels, tgtEntity, waypoints, showHelper)

On load: uses the active server connection (warns if session server differs), checks graph exists (warns if not found), restores label selections, ontology, re-fetches graph data + visualization if previously active, and reopens query panels. If **Auto-run** toggle is on (default), restored queries execute automatically. Session Load/Save/Auto-run controls are in the Sidebar (visible when connected). Schema defined in `tests/session_schema.json`. Session files named with timestamp: `graph_session_YYYYMMDD_HHMM.json` for chronological sort order.

**Session loss protection**: Switching graphs, changing profiles, connecting, or loading a session triggers a red confirmation banner: "Active session for **graph** will be lost" with `[Save & Continue]` `[Continue]` `[Cancel]` buttons. Same red (`#d63031`) used for viz limit warning banner.

- **Graph grammar** (`graphGrammar` state, owned by App): shape `{ COMPONENT: { configurations: [{label, required:[ids]}], optional: [ids] } }` per component. `DEFAULT_GRAMMAR` covers NODES/EDGES/WEIGHTS/RESTRICTIONS with common combos. `graphGrammar` is the legacy view used by the **Create Helper**.
- **Per-endpoint grammar** (`endpointGrammar` state, owned by App): the richer per-endpoint shape from `/show/graph/grammar` → `components_json` → `endpoints`. Normalised to `{ create:{...}, solve:{...}, match:{...}, query:{...} }` where each entry is `{ components: { NAME: { displayName, configurations:[{label, required, filtervalues}], optional:[ids] } }, filterparams, options:[{name, type, default, filtervalues, internal}] }`. Components whose `name` appears more than once (e.g., solve has two `SOLVETARGETS` for source + destination) are role-renamed via `ENDPOINT_ROLE_NAMES` — for `/solve/graph` the two `SOLVETARGETS` entries become `SOURCE_NODES` (1st) and `DESTINATION_NODES` (2nd). The `displayName` carries the role name, which is what's both rendered in the UI and emitted as the `<NAME> => INPUT_TABLES(...)` SQL keyword. `typeName` keeps the original grammar component type (`SOLVETARGETS`) for reference. Unmapped duplicates fall back to a `<NAME>_N` suffix. Filters: configurations and options carry `filtervalues` — e.g., `convergence_limit` is `PAGE_RANK`-only; the Solve Helper hides options whose filtervalues don't include the selected solver. Best-effort fetch from `/show/graph/grammar` on connect; older builds returning the flat `component_grammar` shape are still handled as a fallback for the create endpoint. The Create Helper uses `optional` add-ons to spawn EXTRA rows (with `Optional` placeholder + lighter background) alongside the required ones — e.g., picking EDGES `NODE1 + NODE2 (string)` spawns 2 required + 6 optional rows (EDGE_ID/LABEL/WEIGHT/PARTITION/NODE1_LABEL/NODE2_LABEL). Empty optional rows are skipped on Generate
- **Generic identifier names**: `chGenericId(id, component)` collapses type-specific node identifiers (NODE_NAME/NODE_ID/NODE_WKTPOINT → `NODE`; EDGE_NODE1_* → `NODE1`; EDGE_NODE2_* → `NODE2`) AND strips the section/component prefix (`NODE_LABEL → LABEL` in NODES, `EDGE_ID → ID, EDGE_LABEL → LABEL` in EDGES, `WEIGHTS_VALUESPECIFIED → VALUESPECIFIED` in WEIGHTS, `RESTRICTIONS_VALUE → VALUE` in RESTRICTIONS). The section header already conveys the component context — Kinetica infers the type from the column. Used in both the UI label after "as" and the SQL alias the generated code writes
- **Column auto-complete cache** (`tableColumnsCache` state): lazy `{ 'schema.table': [cols] }` map populated by `/get/records limit:1` when the user types a known `schema.table.` prefix in a Create Helper row. Entries are seeded with `[]` immediately to prevent duplicate fetches on rapid typing. The Create Helper datalist for each row contains EITHER the table-name list (when the user hasn't typed past a known table prefix) OR the specific table's column list (`schema.table.col`) — never both, so browsers reliably handle clicks on multi-option datalists
- **Docs button** (sidebar header) shows `📖 Docs` linking to `../document/Kinetica_Graph_User_Guide.html` in a new tab. Visibility uses optimistic-show: defaults to `true`, runs a HEAD probe on mount, hides only on an explicit 404. The HEAD probe is **skipped under `file://`** because Chrome blocks cross-origin fetch between two local files and logs a CORS error; under file:// we leave the button visible (clicking still navigates to the file directly, browser handles missing-file 404 natively). Under HTTP/static-hosting (e.g., GitHub Pages, `python3 -m http.server` from `graph/`), the probe runs and hides the button cleanly when the doc isn't deployed alongside
- **Stale-closure pitfall on WMS → Deck/Canvas**: `fetchGraphEntities` reads `geoRenderMode` (line ~4584, `useWms = ... && geoRenderMode === 'wms'`) and lists it in its useCallback deps. The handler's `setTimeout` would otherwise capture a `fetchGraphData` whose closure still sees `geoRenderMode='wms'` and re-enter the WMS path. Fix: `fetchGraphData` is mirrored into `fetchGraphDataRef` via a `useEffect`, and the timeout invokes `fetchGraphDataRef.current()` so it always picks up the version built after `geoRenderMode` flipped. If you ever change the deps of `fetchGraphEntities`, keep the ref pattern intact
- **Preserve entity data across WMS round-trips**: `setupWmsMode` overwrites `graphTableData` with a `wmsMode` payload (no parsed nodes/edges), so naively leaving WMS used to drop the entity data and force a Pull+Visualize. Fix: `handleChangeGeoRenderMode` stashes the entity-mode `graphTableData` into `preWmsDataRef` on WMS entry, then restores it on WMS exit. If the user went straight to WMS first (no prior entity fetch), the stash is empty and we fall back to clearing `graphTableData` + collapsing the maximized overlay. `loadGraphDetails` clears `preWmsDataRef.current` on graph change so we don't restore a different graph's data after a switch+WMS round-trip.
- **Viz-limit guard (`bigGraphThreshold` / `setVizConfirm`)** is enforced uniformly across all 4 `Pull+Visualize` `onVisualize` handlers (CanvasGraph, DeckMapView, MapView, empty-state placeholder). Earlier code skipped the check when `geoRenderMode` was `'deckgl'` or `'auto'` — that guard is removed; the dropdown is the single source of truth (`∞` disables). Threshold check runs first; user picks Continue/Cancel from the red banner before fetch starts
- **MapView post-fetch render = reset path** (line ~3217). On every `parsedEdges.count: 0 → N` transition, runs a synchronous `renderCanvas(0)` (decimated, ~5K edges) for instant feedback, then a setTimeout chain `step(1) → step(2) → … → step(maxLod)` at 80 ms intervals, each rendered with `skipClear=true` (additive — keeps the previous LOD's content visible while a slow LOD-N synchronous draw is locking the thread). The chain bails out early if `userInteractedRef.current` flips during the chain, *but* still pins `lodRef.current = maxL` on bailout so subsequent `renderCanvas()` calls (picks etc.) default to full detail
- **MapView blackout pitfalls** (resolved, document for future): (1) `getEdgeColor` was a plain function; the `drawChunkRef`-setup useEffect listed it as a dep, so every re-render churned through cleanup → null `drawChunkRef.current` → chunks dropped. Memoized via `useCallback([labelColorMap])`. (2) `ResizeObserver` would fire a synchronous `renderCanvas(maxLod)` mid-LOD-chain on first mount; gated behind `resetInProgressRef` and now renders at `lodRef.current` (current LOD), not `maxLod`. (3) `scheduleRender(true)`'s settle chain ran concurrently with my reset's chain when the user interacted during fetch — the reset chain bails out the moment `userInteractedRef` changes. (4) `renderCanvas` snapshots the canvas into `preClearSnapshot` before clearing; if the new render would produce a blank canvas (`visibleCount === 0`), restores the snapshot — defensive guard against any rogue `renderCanvas` running with off-data viewport state. (5) Info-overlay band is now cleared on every render (even with `skipClear=true`) so a longer earlier-LOD info text doesn't leak past a shorter later-LOD bg rect (the "stuck LOD 9/10" symptom)
- **MapView edge-pick detail strip** is `position: absolute; bottom: 0; right: 0; left: 0` over the canvas/WMS container (parent has `position: relative`). Earlier flex-sibling layout caused the canvas to shrink ~140 px on the very first pick → ResizeObserver-triggered redraw at smaller dimensions made the user's zoomed view appear to lose the picked edge. Translucent white bg (`rgba(255,255,255,0.95)`) keeps a hint of the data visible underneath. Same overlay pattern as DeckMapView's strip

### `/show/graph` Response Format

Also double-wrapped via `data_str`. Key fields:
